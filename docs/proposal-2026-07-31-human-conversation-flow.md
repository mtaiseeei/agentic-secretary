# 人間らしい会話フローへの再調整

- 記録日: 2026-07-31
- 状態: ユーザー承認済み。Harness Planner の入力
- 対象: `agentic-secretary` 共通core、配布版、`my-vault`版、`yasashii-secretary`版

## 背景

`memory-care` で、ユーザーが「覚えておいて」と明示しているにもかかわらず、
入力全文を一字一句復唱するだけで保存せず、質問もないまま別ターンの了承を待つ事例が発生した。

調査の結果、これは単一Skillの分類ミスではなく、過去の仕様・評価・回帰テストが
安全性を次の形式で代用し、共通rule、copy、style、AGENTSへ固定したことが原因と確認された。

- 別ターンで停止する
- 原文をbyte単位で復唱する
- 質問、説明、2行目を禁止する
- write操作を、明示依頼と自発提案を区別せず再承認へ回す

本調整は安全性を弱めるものではない。明示依頼、自発提案、曖昧さ、破壊的操作、
外部影響を区別し、実際に残っている危険に応じて確認する契約へ改める。

## ユーザー承認

ユーザーは2026-07-31に、調査報告の基本方針へ賛成し、以下を明示した。

- 大きな調整として、単一Sprintで扱ってよい。
- この調査内容を保存したうえでHarnessを回す。
- Planner完了後、Generatorへ渡す前に `claude -p` のFableへ敵対的レビューを依頼する。
- Fableのレビュー結果をPlannerの契約へ取り入れてからGeneratorへ進む。
- それ以降は通常のHarnessループとする。
- リリースを出してよい。
- Notionでは現時点で意図と異なる問題を観測していないため、フロー全体を大きく変えない。
  今回具体的に特定した問題の限定修正にとどめる。
- Notion以外の調査対象は原則として修正する。

## 共通の会話契約

### 1. 明示依頼

「覚えて」「記録して」「メモして」「設定して」「完了にして」等で、
操作、対象、行き先が明確であり、残る危険が小さい場合、その発話自体をauthorizationとして扱う。
別ターンで同じ内容を承認させず、同じターンで実行し、成功後に過去形で報告する。

### 2. 自発提案

秘書が保存、プロジェクト化、設定変更等を自発的に提案する場合は、実際の質問文で事前確認する。
確認待ちでは副作用を起こさない。

### 3. 曖昧さ

対象、日付、行き先、参照先に複数候補がある場合は、不足している一点だけ質問する。
宣言文だけを返して待たない。構造化選択肢は比較が有用な場合だけ使う。

### 4. 別承認を維持する操作

次は、明示依頼であっても対象と影響を示して確認する。

- 削除、上書き、戻しにくい変更
- 公開、push、認証、権限変更、課金
- メール、チャット、assign、mention等、他者への通知を伴う操作
- 大量作成、一括変更
- Secretを含む保存
- 送信先、公開範囲、対象が曖昧な外部操作

### 5. 応答整合

- 実行していない状態で「記録します」「残します」と完了風に宣言しない。
- 待つ場合は、返答が必要だと分かる質問または選択肢を示す。
- 成功後は、何をどの種別・行き先へ保存したかを過去形で伝える。
- 単純な成功は自然な短文、複数結果や部分失敗は必要な構造で示す。
- 次の行動が無い場合に、固定帳票のためだけの「次の一手」を作らない。

### 6. 現在用件の優先

現在の明示依頼を、古い再開しおり、決定の拾い漏れ監査、プロジェクト候補、
内部index整合より優先する。内部管理は現在用件を横取りしない。

### 7. 維持する安全機構

次の機構は維持する。

- path guard
- atomic writeとrollback
- 空上書き拒否
- Secretの保存拒否・非表示
- 未依頼のpush禁止
- 削除、公開、認証、権限変更の確認
- 外部状態を未確認のまま成功扱いしない
- 書込み失敗時に成功を宣言しない
- ユーザー入力にない事実を保存内容へ追加しない

## 共通で修正する主な面

- `memory-care`: 明示保存依頼は即時保存。自発提案だけ質問。原文復唱と質問禁止を廃止
- `settings`: 明示された可逆な設定変更は即時反映。値不足時だけ質問
- `daily`: 明示されたTODO完了・持越しは重複確認しない
- `projects`: 明示されたプロジェクト化と、秘書側の候補提案を区別
- `secretary`: 現在用件を再開しおりより優先
- 会話終了: 決定0件の監査報告を通常の締めへ出さない
- setup: 利用依頼と接続設定依頼を分け、実際に未接続の場合だけsetupへ進む
- update/onboarding: 同じ選択・依頼の重複確認を減らし、重大な境界だけ確認
- response style: 固定3項目、内部stage名、不要な技術証跡の強制を内容依存へ改める
- closed project: 名前等の軽量read-only照合を許し、人工的な忘却を避ける

## my-vault版

my-vaultでは実行タスクの正本がNotion TaskDBであることを維持する。
「日付＋将来行動＋覚えて」のような入力は、キーワードだけでmemory-careやlocal TODOへ送らず、
意味と正本ルールに基づいてNotionタスクと作業上の注意事項として扱う。

ただし、現時点でNotionの通常利用に問題は観測されていないため、Notionフロー全体は再設計しない。
修正は今回確認した次の点に限定する。

- task-triageで番号承認後、内容が変わっていないのに同じタスクを再承認させない
- 明示保存依頼で質問文なしに停止しない
- 日付のある実行行動をlocal TODOへ誤送しない
- Calendarとvaultのread-only横断依頼は内部で分割し、結果を統合する
- 内部用語だけで停止せず、利用者が決める一点を示す

Notionのproperty設計、relation、通常の作成フロー、TaskDB正本、既存の安全条件は、
今回の限定問題を直すために必要な範囲を超えて変更しない。

## yasashii版

- 通常の設定値とSecretを分離する
- 「もっとフランクにして」等の明示設定は、その場で反映して新しい口調で報告する
- 単純成功まで「やったこと／結果／次に何が起きるか」の固定3項目へ押し込まない
- 共通coreの旧復唱文と停止契約をcopy、style、AGENTS、fixtureから除く

## テスト契約

自然文のbyte一致や固定prefixを主な合格条件にしない。
次の状態遷移と意味保存性を検査する。

- intent: explicit / inferred / ambiguous / destructive / external
- side effect: 0 / 1 / partial
- response state: question / saved / error / partial
- 保存された主体、日付、行動が入力と一致する
- 入力にない事実、不要な全文、依頼語を保存内容へ追加しない
- 分類器の境界例を含むgolden setを持つ
- 重複作成、Secret保存、通知を伴う即時実行、複合依頼の中間状態を拒否する

## Harnessの特別手順

この開発は単一の大きなSprintとして契約化する。

1. Plannerが仕様、非対象、受け入れ条件、rubric、単一Sprint契約を作る。
2. Generatorへ進む前に、オーケストレーターが `claude -p` のFableへ敵対的レビューを依頼する。
3. Fableには、安全性の後退、intent誤分類、Notionの過剰変更、版間drift、テストの抜け、
   リリース事故を重点的に探させる。
4. 指摘をPlannerへ戻し、採用・不採用と理由を仕様・Sprint契約へ反映する。
5. 反映済み契約をユーザー承認済みの実装契約としてGeneratorへ渡す。
6. Generator以降は通常のHarnessループで、独立EvaluatorのPASSまで進める。

## リリース

本Sprintはリリースをscopeに含めてよい。ただし、外部公開、remote push、tag、GitHub Release等の
具体的な外部操作は、実装・独立評価・release gateが完了し、対象version、配布先、変更内容、
戻し方を確認した後に行う。
